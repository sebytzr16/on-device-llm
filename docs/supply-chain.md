# Supply-chain verification

These are build-machine checks. They add no update, telemetry or download calls to
the application itself (see the S19/S21 findings in
[the 2026-11-11 audit](audit-2026-11-11/02-security-privacy.md)).

## Enforced today

| Input | Control |
| --- | --- |
| Gradle distribution | `distributionSha256Sum` in [`android/gradle/wrapper/gradle-wrapper.properties`](../android/gradle/wrapper/gradle-wrapper.properties) |
| Dart/Flutter packages | `pubspec.lock` must stay unchanged after `flutter pub get`; enforced in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) |
| llama.cpp, Vulkan headers, compiler ZIP | Pinned revisions and SHA-256 checks in [`scripts/bootstrap.ps1`](../scripts/bootstrap.ps1) |
| Windows release binaries | Optional SignTool signing and `/pa` verification in [`scripts/package-windows.ps1`](../scripts/package-windows.ps1); see [Windows packaging](windows-packaging.md) |

## Gradle wrapper checksum

The wrapper downloads `gradle-9.1.0-all.zip` and the wrapper verifies it against:

```text
distributionSha256Sum=B84E04FA845FECBA48551F425957641074FCC00A88A84D2AAE5808743B35FC85
```

The value is the SHA-256 of the official `services.gradle.org` distribution. A
mismatch makes the wrapper fail instead of running an unexpected distribution.
Third-party mirrors must not be used to obtain this value.

When changing the Gradle version, update `distributionUrl` and
`distributionSha256Sum` in the same change and take the checksum from Gradle:

```powershell
Invoke-WebRequest -UseBasicParsing 'https://services.gradle.org/distributions/gradle-9.1.0-all.zip.sha256'
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\.gradle\wrapper\dists\gradle-9.1.0-all\<DIST_ID>\gradle-9.1.0-all.zip"
```

Gradle dependency verification (`gradle/verification-metadata.xml`) and release
dependency locking are **not implemented yet**. TODO: generate and review
verification metadata for the Android build inputs before a release. Note that
`android/gradlew`, `gradlew.bat` and `gradle-wrapper.jar` are generated by the
Flutter tool and ignored by git (`android/.gitignore`); the committed properties
file still controls the downloaded distribution.

## GitHub Actions pinning

`.github/workflows/*.yml` still uses mutable major-version tags. Pinning to full
commit SHAs is **not done yet** because the exact release commits were not
verified in this change. TODO list:

| Workflow | Action | Current ref | TODO |
| --- | --- | --- | --- |
| `ci.yml` | `actions/checkout` | `@v4` | Pin to the verified commit SHA of `v4`, keep `# v4.x.y` in a comment |
| `ci.yml` | `subosito/flutter-action` | `@v2` | Pin to the verified commit SHA of `v2`, keep `# v2.x.y` in a comment |
| `ci.yml` | `actions/setup-java` | `@v4` | Pin to the verified commit SHA of `v4`, keep `# v4.x.y` in a comment |
| `ci.yml` | `actions/upload-artifact` | `@v4` | Pin to the verified commit SHA of `v4`, keep `# v4.x.y` in a comment |
| `release-device-quality.yml` | `actions/checkout` | `@v4` | Same as above |
| `release-device-quality.yml` | `subosito/flutter-action` | `@v2` | Same as above |
| `release-device-quality.yml` | `actions/upload-artifact` | `@v4` | Same as above |

Resolve a tag to its commit on a machine with network access, for example:

```powershell
gh api repos/actions/checkout/commits/v4 --jq .sha
gh api repos/subosito/flutter-action/commits/v2 --jq .sha
gh api repos/actions/setup-java/commits/v4 --jq .sha
gh api repos/actions/upload-artifact/commits/v4 --jq .sha
```

Then write `uses: actions/checkout@<FULL_SHA> # v4.x.y`. Do not pin from an
unverified third-party page, and do not keep the mutable tag next to the SHA.
Review the diff before updating a pin; Dependabot/Renovate may propose new SHAs,
but each one needs the same review.

## Dart lockfile

`flutter pub get` must not change the committed `pubspec.lock`. CI runs
`git diff --exit-code pubspec.lock` right after `flutter pub get`, so a stale or
newly resolved dependency fails validation. To update dependencies, run the
resolution, review the lockfile diff, and commit both `pubspec.yaml` and
`pubspec.lock`. On the release machine, run the same check before building.

## SBOM and advisory review

Run these steps on the release build machine after a clean `flutter pub get`
(outputs stay under the git-ignored `artifacts/` directory):

1. Dart/Flutter inventory:

   ```powershell
   New-Item -ItemType Directory -Force artifacts/sbom | Out-Null
   flutter pub get
   git diff --exit-code pubspec.lock
   dart pub deps --json | Set-Content -Encoding utf8 artifacts/sbom/pub-deps.json
   dart pub deps --style=compact | Set-Content -Encoding utf8 artifacts/sbom/pub-deps.txt
   dart pub outdated | Set-Content -Encoding utf8 artifacts/sbom/pub-outdated.txt
   ```

2. Android/Gradle inventory (after the first Android build has generated
   `android/gradlew.bat`):

   ```powershell
   Push-Location android
   .\gradlew.bat dependencies --configuration releaseRuntimeClasspath |
     Set-Content -Encoding utf8 ..\artifacts\sbom\gradle-dependencies.txt
   Pop-Location
   ```

3. Native inventory: record the pinned llama.cpp revision, Vulkan/SPIRV header
   revisions, compiler archive hash and the bundled runtime DLL versions from
   `scripts/bootstrap.ps1` and `engine-manifest.json`.

4. Advisory review: check the resolved Dart packages against the GitHub Advisory
   Database for Pub (<https://dart.dev/tools/pub/security-advisories>) and OSV
   (<https://osv.dev/>), and the Gradle/native components against the same
   sources plus the upstream projects' security notices. A version age is not a
   finding; record the resolved version, affected range, reachability and the
   fix or exception.

5. Licence review: compare the SBOM and new components with
   `THIRD_PARTY_NOTICES.md` and the runtime licence registry, and record any new
   or changed licence before release.

6. Release record: store `artifacts/sbom/`, the `pubspec.lock` SHA-256, the
   commit id, the Gradle distribution SHA-256, the bundled native revisions and
   the SHA-256 of every published Windows artifact with the release. Review the
   Windows publisher name and signature on a clean machine before publishing
   (see [Windows packaging](windows-packaging.md)).

Exceptions must name the component and version, why it is accepted, who owns it,
the compensating control and the review date. Do not add an automatic
advisory-check or update call to the app; these checks belong on the release
machine.
